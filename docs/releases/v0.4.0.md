The default public/STDIO profile is `models-weave`. MT SaaS selects
`models-weave-agents`, `shared`, and `read-write`. Dedicated selects
`models-only` or `models-weave`, `dedicated`, and its access mode. Managed v0.4
rejects the local-only ARIA and extra GraphQL-tool profiles. This does not
disable GraphQL mode on `query_wandb_tool`. The previous per-feature variables are a
breaking migration: their presence fails startup rather than being ignored.
Tool visibility is only a deployment envelope; every call still uses the
request-scoped W&B identity and authorization checks.

### SDK-first reads with GraphQL compatibility

`query_wandb_tool` supports structured SDK reads and legacy `query`/`variables`
inputs under the same public tool name. Both modes are available in Shared,
Dedicated, and local workloads and in both access modes. Existing query-only
callers do not need to select another profile or rename the tool.

Structured mode reads projects, runs, sweeps, and reports through bounded W&B
read APIs. Fixed application-owned query-only projections are used where they
avoid SDK fan-out or select only the requested fields. GraphQL mode uses the
same bounded query engine as the existing compatibility tool, with defaults
`max_items=100` and `items_per_page=20`. It rejects mutations, subscriptions,
multiple operations, and mixed GraphQL/structured inputs before backend work.

Run collections return core metadata by default. Callers can request:

- `summary_keys` for specific summary metrics.
- `config_keys` for specific configuration values.
- Full `summary`, `config`, `system_metrics`, or related details for bounded
  result sets, subject to the response budget.
- `cursor` continuation for collection reads that return `next_cursor`.
- `response_mode="count"` for an exact server-side run count.

Individual run lookups support the modeled run fields plus requested details.
History, files, and artifacts remain separate bounded reads. Collection-wide
full detail is intentionally limited because loading every field from many wide
runs can degrade the W&B application for other users.

### Explicit scope and accuracy

Collection, history, artifact, registry, schema, and evaluation tools now stop
at their configured bounds and report coverage explicitly. Depending on the
tool, responses include fields such as:

- `total_count` and `returned_count`
- `has_more`
- `project_exhaustive`
- `sampled`
- `truncated`

History reads support bounded range scans, custom axes, and target-value
verification. Analysis tools use selective server-side fields instead of
materializing complete run objects whenever the W&B API supports projection.

Registry organization inference now stays on the authenticated,
request-scoped W&B client. Explicit organization input wins; otherwise one
accessible organization is selected automatically, while ambiguous accounts
receive a bounded `organization_required` response instead of a Python
exception. Registry, collection, and registry-version reads share that result.
Collection listings no longer trigger one lazy alias request per collection;
they return `aliases: null` and `aliases_loaded: false`, and callers use
`list_artifact_versions_tool` for actual version aliases. Project artifact tag
filters are applied after a bounded SDK page scan, so a missing tag returns a
successful, explicitly bounded empty result instead of scanning pages until a
generic API failure.

### Correct multi-key history

For explicit multi-key default-history sampled and ranged collection reads,
`get_run_history_tool` now returns an outer union for requested metrics logged
in different `wandb.log()` calls or at different cadences. A fixed,
application-owned query-only projection retrieves one bounded series per key in
batches of at most eight and merges them by `_step`, falling back to the selected
x-axis. The path is designed to cover active/unexported and exported history
without one network roundtrip per key. Multi-request reads use the same freshly
observed upper-step boundary for every batch. A fixed snapshot query reads run
identity fields and one complete, resume-oriented `historyTail` row, so history
does not first load the run's complete config, summary, system metrics, or
history-key index. The tail row itself is subject to the same post-protobuf
GraphQL safeguards described below. This path is part of the normal read
surface in every supported managed tool profile; callers cannot supply or
modify the query.

`samples` remains the total final-row budget across all keys. Range reads remove
rows containing none of the requested values before deterministic, key-aware
sampling, retaining all observed sparse points in the bounded result when
capacity permits. If limits prevent complete representation, the response
identifies the affected keys.
New additive metadata includes `requested_keys`, `join`, `matching_rows`,
`matching_rows_exact`, per-key observed and returned counts, `unobserved_keys`,
`missing_keys`, `keys_omitted_by_limits`, `non_finite_counts`, and whether the
counts are exact.
No usable finite/non-null value in a sampled/bounded result is reported as
unobserved; a key is called missing only when the read produced exact counts.
Custom x-axis values must co-occur with
their metric, and exact `target_x` remains a point lookup.
`source_truncated` reports when a source scan is clipped by the configured step
window or row cap, including duplicate or forked rows that exceed the step span.
`source_values_truncated` counts source rows containing an oversized value
replaced by a bounded sentinel; either condition sets `truncated=true`.
`non_finite_counts` records NaN and positive/negative Infinity observations in
the bounded source. Those values are omitted from returned JSON, and their counts
are exhaustive only when `key_counts_exact=true`.

### Evaluation prediction reconciliation

`summarize_evaluation_tool` now counts only direct
`Evaluation.predict_and_score` children of each `Evaluation.evaluate` root.
Bookkeeping and summary siblings, along with nested prediction-like calls, are
excluded so prediction totals, coverage, and bounded detail aggregates describe
the same evaluation rows.

The Python package also constrains the MCP SDK to the compatible 1.x API. MCP
SDK 2.x removes the `mcp.server.fastmcp` module used by this release.

STDIO deployments now force analytics and startup logs to stderr, including
when `MCP_ANALYTICS_LOG_STREAM=stdout` is set. Standard output remains reserved
exclusively for MCP JSON-RPC messages.

### Opt-in asynchronous ARIA conversations

Local deployments with an approved hosted W&B Agent endpoint can select
`WANDB_MCP_TOOL_PROFILE=models-weave-agents-aria` to add three asynchronous
tools for starting, polling, and batch-polling ARIA turns. The group is absent
from every managed v0.4 profile, and
every opt-in ARIA request identifies its client as `wandb-mcp-server/<version>`
for server-derived product analytics attribution. This header is not used for
authentication, authorization, routing, quotas, or billing.
Dedicated/Self-Managed and MT SaaS cannot enable ARIA in managed v0.4. A future
managed opt-in requires a separately reviewed entitlement, network, credential,
and data-residency design.

Submission is treated as a non-idempotent write and is never automatically
retried. Polling duration, input sizes, concurrent requests, total polling
requests, and raw turn responses are bounded. With
`WANDB_MCP_ACCESS_MODE=read-only`, the polling tools remain available while
`aria_send_message` is omitted.

### Workload protection

Signed HTTP sessions now survive idle-cache expiry and instance changes while
remaining bound to the caller's current credential. The session TTL limits idle
local state; it does not expire the credential or grant access on its own.
Active requests retain their session until the response finishes, and session
capacity failures are reported separately from authentication failures.

Malformed tool arguments pass through normal input validation without leaking
request context or admission capacity. Documentation search now bounds both
the upstream download and successful response text. Token counting uses a
checksum-verified vocabulary included in the package, with no runtime download
or writable-cache requirement.

Weighted admission control is available at the public tool boundary. The
Dedicated profile enables it; MT SaaS uses bounded infrastructure concurrency
with application admission disabled:

- Light calls cost 1 unit.
- Collection and history calls generally cost 2 units.
- Broad analysis, full-detail, and raw GraphQL calls cost 4 units.

Dedicated calls wait for capacity for up to two seconds. If capacity remains
unavailable, the server returns:

```json
{
  "error": "server_busy",
  "retryable": true,
  "retry_after_ms": 1000
}
```

This is a controlled overload response, not a W&B data error. Clients should
wait for `retry_after_ms` and retry rather than starting additional concurrent
calls.

A separately capacity-managed hosted runtime may explicitly disable the
application-level admission controller. That does not disable tool deadlines,
W&B request timeouts, pagination limits, response budgets, or infrastructure
concurrency limits. Deployment owners must validate that profile under load.

The exact workload and capacity defaults are generated from the packaged
runtime contract above. A timed-out synchronous worker retains its admission
permit until it actually finishes, preventing replacement work from exceeding
physical concurrency. Managed profiles reject individual numeric overrides;
bounded advanced tuning is local-only.

### Dedicated and Self-Managed routing

Dedicated installations can keep client access and user-facing links on the
public instance URL while sending backend MCP-to-W&B calls over a
namespace-local Kubernetes service:

```bash
WANDB_BASE_URL=https://your-instance.example
# The chart supplies WANDB_INTERNAL_BASE_URL for supported topologies.
MCP_WORKLOAD_PROFILE=dedicated
MCP_CAPACITY_CLASS=small
```

The Dedicated Helm chart resolves the split-API or monolithic service address
for the installation. Nonstandard or external topologies use the typed
`mcp-server.routing.internalBaseUrl` value.

API-key validation, W&B SDK clients, report creation, analysis logging, run
history, and the optional raw-query transport use the resolved internal URL.
The server does not silently retry through the public ingress if an explicitly
configured internal URL fails.

This setting routes W&B Models/API calls. Weave trace traffic remains
independent and uses `WF_TRACE_SERVER_URL`.

Public project, run, sweep, and report links continue to use
`WANDB_BASE_URL`; internal service names are not returned to clients.

### Safer query and write boundaries

The legacy GraphQL mode on `query_wandb_tool` is available in every supported
workload, including `shared` and `dedicated`, and remains read-only. Supply
`query` and optional `variables`; do not combine them with structured SDK
selectors. Query documents, variables, pagination, deadlines, and returned
results remain bounded, using the caller's existing W&B authorization.

The separate `query_wandb_graphql_tool` is still available only through the
explicit local compatibility profile:

```bash
WANDB_MCP_TOOL_PROFILE=models-weave-graphql-compat
MCP_WORKLOAD_PROFILE=local
```

That profile adds the extra tool; it is not required for legacy
`query_wandb_tool` callers. Both entry points accept exactly one GraphQL query
operation. Mutations, subscriptions, multiple operations, and mixed-mode inputs
are rejected before a W&B request. Tool names, exact profile counts, resource
defaults, and write-tool visibility are unchanged.

On the supported W&B ServiceApi path, the MCP rejects a GraphQL `data_json`
payload above 16 MiB before its own `json.loads` call and rejects decoded
responses above 500,000 nodes. These safeguards return `response_too_large`
and bound MCP-side JSON/object/output processing. They run after the SDK
receives the protobuf envelope, so they are not a wire-size or backend-work
limit.

For deployments that must expose no MCP write tools:

```bash
WANDB_MCP_ACCESS_MODE=read-only
```

This omits `create_wandb_report_tool`, `log_analysis_to_wandb`, and the opt-in
`aria_send_message`. Access mode only subtracts capabilities from the selected
tool profile.

Use these reviewed presets:

| Deployment | Settings |
|---|---|
| MT SaaS | `models-weave-agents`, `shared`, `read-write` (30 tools) |
| Dedicated Models-only | `models-only`, `dedicated`, `read-write` (17 tools) |
| Dedicated with classic Weave | `models-weave`, `dedicated`, `read-write` (22 tools) |
| Local extra GraphQL tool | `models-weave-graphql-compat`, `local`; access mode selected independently |

### Telemetry quality and privacy

An explicitly empty or invalid `MCP_LOG_PRIVACY_LEVEL` fails startup rather
than silently selecting `off`. The existing unset default and valid `off`,
`standard`, and `strict` behavior are unchanged.

Telemetry now:

- Attributes supported clients such as Codex, Claude Code, Claude Desktop, and
  Cursor separately from their vendor.
- Emits one event at the public MCP boundary for each tool invocation.
- Records the exact MCP method and public tool name.
- Uses an authenticated W&B username in canonical logs and Datadog at
  `off`/`standard` when it was supplied by authentication or already
  materialized in that actor's API-client cache. Otherwise, the user identity is
  omitted rather than displaying a hash. Segment retains its existing pseudonymous IDs.
  Identity inspection never evaluates a lazy viewer
  property or makes an extra lookup, and it never substitutes an entity or
  email for a username.
- Keeps the API-key-derived SHA-256 pseudonym in canonical logs and Datadog at
  `strict`. Segment always receives a pseudonym at every privacy level and never
  receives a raw username. This is pseudonymization, not anonymity.
- Excludes API keys and raw tool arguments from product events. Allowlisted,
  bounded usage dimensions describe operation shape without copying prompts,
  queries, filters, or report content.
- Avoids recording Weave request bodies, trace identifiers, selected customer
  fields, or upstream response bodies in application logs, including error and
  debug paths.
- Bounds dimensions and serialized event size.
- Keeps one Datadog user field (`usr.id`), one success field, and the reserved
  nanosecond duration field. Removes the duplicate labels object and identical
  implementation/public tool aliases while retaining existing dashboard queries.
- Preserves bounded error categories and validation field names through wrapped
  exceptions, without copying argument values or upstream error bodies. This
  distinguishes rejected inputs from authentication, permission, not-found,
  timeout, and backend failures when the underlying exception provides that
  information.

Successful HTTP request telemetry is sampled for operational cost control.
Session and public tool events are not sampled.

Agent observability reads also perform one upstream attempt. A trace-service
rate limit or overload is returned as retryable `server_busy` with a bounded
`retry_after_ms`, so the MCP server does not amplify upstream pressure with
hidden retries.

### Security and CI hardening

The release updates security-sensitive dependencies, including MCP, GitPython,
and the development/test dependency set. The reproducible release lock includes
W&B 0.28.0, W&B Workspaces 0.4.4, and GitPython 3.1.59; the GitPython minimum
is 3.1.58 so fresh installations do not resolve a known-vulnerable release.

CI now:

- Pins third-party GitHub Actions and the uv tool version.
- Scans locked dependencies with Grype.
- Scans Python source with Bandit.
- Retains the Grype report as a workflow artifact.
- Requires the repository's external Socket Security check, Python 3.11/3.12
  tests, W&B-latest compatibility, and fresh-wheel construction checks. Socket
  results are GitHub check evidence rather than an in-repository scanner command.

## Query compatibility and structured reads

v0.3.x callers can continue passing a query-only GraphQL document through the
legacy `query`/`variables` interface on `query_wandb_tool`. The optional pagination
arguments retain defaults `max_items=100` and `items_per_page=20`, subject to the
active workload's bounds. Refresh cached tool definitions after upgrading.

Structured SDK reads remain available through the same tool:

```text
query_wandb_tool(
  entity_name,
  project_name,
  resource,
  run_id?,
  sweep_id?,
  report_name?,
  filters?,
  order?,
  limit?,
  include?,
  summary_keys?,
  config_keys?,
  response_mode?,
  cursor?
)
```

For `resource="reports"`, `report_name` accepts either an exact internal report
name or the exact user-visible report title.

Use the existing specialized tools for entity/project discovery, run history,
artifacts, registries, automations, and integrations. If a required read shape
has no SDK equivalent, use `query_wandb_tool(query=..., variables=...)`. Do not
mix those arguments with structured selectors in one call. The additional
`models-weave-graphql-compat` profile remains local-only, but it is no longer a
prerequisite for using GraphQL through the original tool.
See the [query capability matrix](../query-capabilities.md) for exact routing.

## Operator settings

The release-controlled selectors and defaults are generated from the packaged
contract above. Deployment-specific URLs remain orthogonal:

| Setting | Default | Purpose |
|---|---|---|
| `WANDB_INTERNAL_BASE_URL` | Unset | Server-side W&B API URL |
| `WB_AGENT_BASE_URL` | Unset for explicit local ARIA selection | Approved absolute HTTPS ARIA service origin |

The five v0.3 per-feature/read-only variables are removed. If any is present,
v0.4 fails startup with a bounded migration error instead of silently choosing
a different public manifest. Managed workload profiles also reject direct
numeric overrides of release-critical limits, deadlines, admission, sessions,
and workers; validated low-level tuning remains available only in `local` mode.
Operator-supplied `MCP_HOSTED_MODE` is also removed: use
`MCP_WORKLOAD_PROFILE=shared` for MT SaaS or `dedicated` for Dedicated instead.

See the [README](../../README.md#command-line-reference) for the complete
configuration reference.
